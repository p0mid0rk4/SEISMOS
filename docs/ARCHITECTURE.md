# Архитектура СЕЙСМОС

Документ описывает структуру системы, потоки данных и назначение модулей.

## 1. Общая схема

```
Полевой сегмент → Узел сбора → Движок обработки → Хранилище → API → Консоль
```

Система разделена на четыре слоя, каждый из которых можно развивать и
тестировать независимо:

| Слой | Модули | Ответственность |
|---|---|---|
| Аппаратный | `seismos/hardware` | Датчики, АЦП, узел сбора, цепочка |
| Обработки сигналов | `seismos/detection` | Фильтрация, обнаружение, классификация |
| Ядро | `seismos/core` | Модели, конфигурация, реестр, движок, хранилище, шина |
| Прикладной | `seismos/api`, `seismos/cli`, `console` | API, командная строка, веб-консоль |

## 2. Потоки данных

```
GS-20DX ──(напряжение)──► АЦП ──(В)──► нормировка ──(мкм/с)──► узел сбора
                                                                   │
                                             UDP-пакеты (Ethernet/PoE)
                                                                   ▼
ChainReader ──► ChainSample ──► ProcessingEngine.ingest
                                       │
                                       ▼
                          SeismicDetector.process
                       (фильтр → СКЗ → STA/LTA → CFAR → признаки)
                                       │
                                       ▼
                          Classifier.classify → уровень
                                       │
                                       ▼
                     DetectionEvent ──► EventStore (SQLite)
                              │            │
                              │            └─► Alarm (при уровне ≥ 2 и охране)
                              ▼
                        EventBus.publish
                              │
                    ┌─────────┴──────────┐
                    ▼                    ▼
              WebSocket /ws        REST-выборки
                    │
                    ▼
             Консоль оператора
```

### Единица данных — `ChainSample`

`ChainSample` — блок отсчётов одного датчика (скорость грунта в мкм/с),
с меткой времени и порядковым номером. Именно эти объекты движок принимает
на вход, что позволяет питать систему как от реального узла сбора, так и от
генератора синтетических сигналов.

## 3. Модули ядра

### `core/models.py`

Доменные модели на Pydantic:

- `Sensor` — датчик на периметре (позиция, зона, чувствительность);
- `Zone` — зона охраны (участок периметра, приоритет, режим охраны);
- `DetectionEvent` — событие обнаружения (класс, уверенность, признаки);
- `Alarm` — тревога с жизненным циклом (`active → acknowledged → reset`);
- `SystemStatus` — сводное состояние системы;
- перечисления `EventKind`, `EventLevel`, `EventClass`, `SystemState`,
  `AlarmState`, `SensorKind`.

### `core/config.py`

- `Settings` — настройки приложения (порт, БД, токен доступа, параметры
  детекции). Читаются из окружения `SEISMOS_*` и `.env`.
- `SiteConfig` — описание объекта из `config/site.yaml`.
- `DetectionParams` — параметры алгоритмов обнаружения.
- `ChainConfig` — параметры цепочки геофонов.

Кэш настроек реализован через `lru_cache`; функция `reload_settings()`
сбрасывает кэш (используется в тестах).

### `core/registry.py`

`Registry` строит из конфигурации реестры датчиков, зон и цепочек и
предоставляет выборки: датчики зоны, соседи по цепочке, сводка по
оборудованию. Порядок датчиков в цепочке определяется полем `chain_index`.

### `core/engine.py`

`ProcessingEngine` — центральный узел:

- держит по одному `SeismicDetector` на датчик (состояние STA/LTA и CFAR
  не разделяется между каналами);
- управляет режимом охраны (`arm` / `disarm` / `set_state`);
- формирует `DetectionEvent`, сохраняет их и порождает `Alarm` при уровне
  ≥ «тревога» в поставленной на охрану зоне;
- ведёт квитирование и сброс тревог с записью в журнал аудита;
- рассылает события подписчикам через шину;
- умеет обслуживать фоновые циклы чтения цепочек (`run_chain`, `start`,
  `stop`).

### `core/store.py`

`EventStore` — асинхронное хранилище на SQLite. Записи выполняются в
отдельном потоке (`asyncio.to_thread`), чтобы не блокировать событийный
цикл. Дополнительно ведётся кольцевой буфер последних событий для быстрой
выдачи в WebSocket. Таблицы: `events`, `alarms`, `audit`.

### `core/bus.py`

`EventBus` — широковещательная шина. Каждому подписчику соответствует
очередь ограниченного размера; при переполнении отбрасывается самое старое
сообщение, чтобы медленный подписчик не тормозил обработку сигнала.

## 4. Слой обработки сигналов

### `detection/dsp.py`

Примитивы ЦОС на NumPy: полосовой фильтр `BandPass` (каскад биквадных
секций), `envelope`, `rms`, `zero_crossing_rate`, `spectral_features`
(доминирующая частота, спектральный центроид, спектр).

### `detection/staltl.py`

- `STALTA` — рекурсивные окна «короткое / длинное»;
- `CfarDetector` — адаптивный порог (Cell-Averaging CFAR);
- `SeismicDetector` — полный конвейер одного канала: фильтрация → СКЗ по
  кадрам → STA/LTA → CFAR → удержание события → извлечение признаков.

### `detection/classifier.py`

`Classifier` — экспертный (правиловый) классификатор. Для каждого класса
задан эталонный профиль признаков; оценка — произведение гауссовых функций
подобия по частоте, длительности активной части и амплитуде. Таблица
`CLASS_LEVEL` отображает класс на уровень тревоги.

Обоснование выбора экспертной модели: прозрачность решения для оператора и
предсказуемость поведения на объекте (см. [DETECTION.md](DETECTION.md)).

## 5. Аппаратный слой

### `hardware/geophone.py`

`GeophoneModel` — электромеханическая модель GS-20DX (передаточная функция
второго порядка), перевод «напряжение → скорость» и «скорость → мкм/с»,
расчёт АЧХ, дискретный фильтр отклика, проверки температуры и наклона.

### `hardware/adc.py`

- `ADS1256` — драйвер 24-битного АЦП по SPI (регистровый доступ);
- `SimulatedADC` — программный источник отсчётов для стендов;
- `ADCChain` — последовательный опрос каналов одного АЦП.

### `hardware/node.py`

`SensorNode` — узел сбора: оцифровка группы датчиков, нормировка, упаковка
в UDP-пакеты (сигнатура `SMS1`), передача по сети. `UDPReceiver` принимает
пакеты от узлов. Формат пакета: `magic(4) + sensor_id(2) + seq(4) + ts(8) +
n(2) + отсчёты(int16)`.

### `hardware/chain.py`

`ChainReader` — последовательный опрос цепочки: циклически считывает блоки
со всех датчиков и формирует список `ChainSample`. Работает как с узлом
сбора, так и напрямую с АЦП. Есть синхронный (`stream`) и асинхронный
(`astream`) режимы.

### `hardware/simulator.py`

`SeismicSignalGenerator` — генератор синтетических сигнатур воздействий
(шаги, группа, техника, подкоп, перелаз, удар, метео) для стенда, тестов и
демонстрации.

## 6. Прикладной слой

### `api/app.py`

`create_app()` собирает приложение FastAPI: контекст, реестр, хранилище,
шину, движок; регистрирует обработчики REST, WebSocket и раздачу консоли.
Проверка токена доступа (если задан) вынесена в зависимость
`auth_dependency`. Жизненный цикл приложения оформлен через `lifespan`
(инициализация хранилища на старте, остановка движка и закрытие БД на
выходе).

### `api/context.py`

`AppContext` — общий контейнер объектов, доступных обработчикам
(настройки, реестр, хранилище, шина, движок).

### `cli/main.py`

Команды `serve`, `simulate`, `selftest`, `sensors`, `version`.

### `console/`

Одностраничная веб-консоль (HTML/CSS/JS) без внешних зависимостей.

## 7. Расширяемость

- **Новый тип датчика** — добавьте значение в `SensorKind` и обработку в
  слое сбора; движок работает с любым источником `ChainSample`.
- **Новый класс воздействия** — добавьте значение в `EventClass`, профиль в
  `_PROFILES` и строку в `CLASS_LEVEL`.
- **Интеграция с внешними системами** — подпишитесь на шину или используйте
  WebSocket; события содержат все признаки для внешней аналитики.
- **Другой транспорт сбора** — реализуйте `ChainReader`-совместимый источник
  (`udp`, `tcp`, `file`, `spidev`) и передайте его в `engine.start()`.
